Pricing recommendation - May 16, 2026

Sell predictable plans, meter the expensive tail.

Hetchy's direct infrastructure cost per ordinary run is low. The pricing risk is not the median run; it is unbounded long-running sandboxes, failed runs left for debugging, and future heavier repos. The clean model is a monthly plan with included run credits, where one credit covers a bounded 15-minute Standard sandbox window. Longer runs and larger sandbox flavors consume more credits.

$0.037 Conservative Daytona cost for one 15-minute Hetchy run on today's 2 vCPU / 3 GiB / 4 GiB sandbox.
7.66 min Average app-recorded duration across 10 local Hetchy agent runs from May 13-14, 2026.
1x-6x Recommended credit multipliers across Light, Standard, Pro, and Max sandbox flavors.

Recommendation

Use "run credits" publicly, not raw CPU tokens. A run credit is a simple customer-facing unit: one Standard agent turn, up to 15 minutes of sandbox runtime.

Overage Rule

Charge by started 15-minute block, then multiply by sandbox flavor. This protects margins without making normal customers think about seconds.

Positioning

Price against engineering time saved, not Daytona cost. The cost floor is cents; the value ceiling is avoided developer hours and faster PR throughput.

Sandbox Flavor Model

Keep Standard as the base unit

Plans should include Standard run credits. Larger sandboxes do not need separate plan currencies: they simply consume more credits per started 15-minute block.

credits = started_15_min_blocks * flavor_multiplier started_15_min_blocks = ceil(run_minutes / 15)

Why multipliers beat pass-through

The multiplier should be rounded above pure Daytona cost ratio. Bigger sandboxes tend to mean bigger repos, longer test runs, more debugging time, and higher variance. The extra margin buys that risk down.

Server allocation is a working assumption for app servers, database, logs, cache-volume storage uncertainty, and operational overhead.

Why this model works

Customers get a fixed monthly number they can approve, while Hetchy avoids subsidizing pathological usage. The credit block maps to the actual cost driver: active sandbox minutes. It is easier to explain than token accounting and harder to game than "unlimited runs."

Billing rules to write into the product

  • A run credit covers one Standard fresh run or follow-up turn up to 15 minutes.
  • Every started additional 15-minute block consumes another block of credits.
  • Sandbox flavor multiplies the block: Light 1x, Standard 1x, Pro 3x, Max 6x.
  • Admins choose allowed flavors at the org level and a default flavor per repo.
  • Failed and cancelled runs consume credits because Daytona cost is still incurred.
  • Free trial runs should hard-stop at the limit; paid plans can overage by default with admin controls.
  • Set an account-level monthly overage cap and a per-run maximum runtime to prevent surprise invoices.
  • Enterprise can buy committed credit pools and custom concurrency.

Implementation Notes

Product instrumentation

Add a billing meter table that records sandbox ID, run ID, start time, stop/archive time, CPU, memory, disk, flavor, multiplier, credits consumed, and terminal state. Do not depend on chat history for billing.

Cost controls

Keep stop-and-archive on successful runs. Add cleanup alerts for failed runs left running, and consider a forced archive after a debugging grace period unless an admin pins the sandbox. Gate Pro and Max behind org-level controls and monthly overage caps.

Suggested launch posture: start with Starter, Team, Growth, and "Business / Enterprise" sales-assisted. Keep the included credit bundles generous enough to feel fixed, but make overage visible in admin settings before teams hit it.
